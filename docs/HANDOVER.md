# Handover: TEI-Aware Machine Translation (Ancient Greek → English)

Nov 19, 2026 · @Ennio Fattiboni

## Project summary

Build a tool that translates TEI XML documents from Ancient Greek to English while keeping the document valid and respecting what each tag means. The first corpus is the Perseus Digital Library's canonical-greekLit repository on GitHub. The design must stay language-pair agnostic, so other source and target languages can be added later.

Generic MT tools (DeepL, Google Translate) fail here: they translate text that must stay untouched (foreign-language quotes, attributes), corrupt names, and alter tags. Our tool fixes this by never letting the MT model see the XML structure, and by applying explicit per-tag rules.

This doc is the handover for starting implementation. Read it fully before writing code; the first tasks and the open questions are near the end.

## Decisions already made

The approach combines three methods: tree-level segmentation, detag-and-project, and a configurable tag-policy layer. These choices are settled; do not switch to an end-to-end approach without discussing it with the team.

| Decision | What it means for the code |
| --- | --- |
| Tree-level segmentation | Parse TEI, send only block-level text segments to MT, write translations back into the same nodes. Structure is never generated by a model. |
| Detag-and-project for inline tags | Strip inline tags before MT, record their spans, re-insert them on the English side using word alignment. |
| Tag-policy layer | A declarative rules table decides per TEI construct: translate, protect, or apply a name convention. Rules live in config, not code. |
| Dedicated MT models, run locally | Prefer models that run on a laptop or single consumer GPU (or Colab). A cheap LLM API is allowed only as a reference baseline. |
| Pluggable MT engine | The MT model sits behind one small interface. Changing language pair = changing config, not pipeline code. |
| Pluggable aligner | Default to a multilingual aligner; allow a language-specific one (UGARIT for Greek). |
| Prose before verse | Get the pipeline working end to end on prose (Xenophon, Thucydides, Plutarch) before tackling `<l>` verse lines. |

## Pipeline architecture

The pipeline has six stages, run per document. Only stage 4 depends on the language pair.

1. **Parse and segment.** Load the TEI file with lxml. Walk the tree and collect translatable block segments (`<p>`, groups of `<l>`, citation-unit `<div>`s). Everything structural stays outside the MT model.
2. **Apply the tag policy.** Classify each inline element as translate, protect, or name-convention using the rules table.
3. **Mask and detag.** Replace protected spans with placeholders such as `⟦P3⟧`. Strip remaining inline tags and record their character offsets, attributes and IDs.
4. **Translate.** Send plain-text segments to the configured MT engine.
5. **Restore and project.** Put protected content back byte-for-byte. Use word alignment to re-insert each inline tag around the matching English words, then re-attach its attributes by ID.
6. **Validate and fall back.** Check well-formedness, TEI schema validity, and that every source tag and `@n` value has a counterpart. On projection failure, apply a safe fallback and record it.

Suggested repo layout (adjust freely):

```
tei_mt/
  tei/          # parsing, segmentation, write-back (stages 1, 5 write-back, 6)
  policy/       # rules table loader + classifier (stage 2); rules in config/policy.yaml
  masking/      # placeholders, detag, offset bookkeeping (stage 3)
  engines/      # MTEngine interface + implementations (stage 4)
  align/        # Aligner interface + awesome-align / UGARIT wrappers (stage 5)
  names/        # per-language name-convention plug-ins (LGPN, gazetteer)
  data/         # Perseus loading, CTS-unit pairing, sentence alignment, splits
  eval/         # structural, translation and tag-policy metrics
  cli.py        # translate / evaluate / bakeoff commands
config/
  pairs/grc-en.yaml   # engine, aligner, name convention for this pair
  policy.yaml
tests/          # small TEI fixtures with expected outputs
```

Key interfaces: `MTEngine.translate(segments: list[str], src: str, tgt: str) -> list[str]` and `Aligner.align(src_tokens, tgt_tokens) -> list[tuple[int, int]]`. Keep both batch-oriented so GPU models run efficiently.

## Tag-policy rules (initial)

These are the starting rules. Implement them as config in `policy.yaml` so the team can change them without touching code, and log which rule fired for each element (needed for evaluation).

| TEI construct | Action |
| --- | --- |
| `<teiHeader>`, `@n`, `@xml:id`, `<pb>`, `<lb>`, `<milestone>`, all attributes | Never touch. Update `@xml:lang` on `<text>`; add a `<respStmt>` recording machine translation and the engine used. |
| `<foreign>`, `<quote>` / `<q>` whose `@xml:lang` differs from the source language | Protect: mask with a placeholder, restore byte-for-byte. |
| `<persName>`, `<placeName>`, `<name>` | Translate via the name-convention plug-in; keep `@ref` / `@key`. |
| `<choice>` with `<sic>`/`<corr>` or `<orig>`/`<reg>` | Translate the corrected or regularized reading only (configurable). |
| `<gap>` | Keep as an empty element; never generate text for it. |
| `<supplied>`, `<unclear>`, `<add>` | Keep the tag; translate its content. |
| `<del>` | Keep the tag; default is to leave content untranslated (to confirm). |
| `<l>` (verse lines) | Translate at sentence level across lines, then project line boundaries; alternative: English as prose with `<lb n="…"/>` milestones. Deferred until prose works. |
| `<note>` | Detect the note's language first; translate only if it is in the source language. |
| `<hi>`, `<emph>` and other inline formatting | Translate content; project the tag. |
| Unknown elements | Default to translate-content + project, and log a warning listing the element name. |

For names, the convention is a per-pair option: Latinized (Achilles), direct transliteration (Akhilleus), or keep the original script. Default for grc→en: Latinized, using the Lexicon of Greek Personal Names (LGPN) for people, Pleiades for places, and a gazetteer mined from Perseus English translations for mythological names (LGPN excludes those).

## MT engines

No released model translates Ancient Greek to fluent English well out of the box, so the plan is a zero-shot bake-off first, then LoRA fine-tuning of the best local candidate.

**Step 1 — bake-off.** Translate about 100 held-out Perseus sentences with each candidate and score with chrF and COMET against the Perseus English.

| Candidate | Hugging Face ID / source | Notes |
| --- | --- | --- |
| MADLAD-400 3B | `google/madlad400-3b-mt` | Lists Ancient Greek (`<2grc>` tag); grc quality unreported. Front-runner for a local model. Check its tokenizer handles polytonic Greek. |
| Pivot chain | `ilsp/nllb-200-600M-ag-mg-lora` then `Helsinki-NLP/opus-mt-tc-big-el-en` | Ancient→Modern Greek, then Modern Greek→English. No training needed; errors compound. |
| Opus-MT | `Helsinki-NLP/opus-mt-grk-en` | Its own benchmark reports BLEU 4.1 on Ancient Greek; expected lower bound. |
| LLM reference | A small, cheap API model or a local 4–12B model (e.g. TranslateGemma) | Reference ceiling only, not the core system. |

**Step 2 — fine-tune.** LoRA fine-tune the winner on the Perseus parallel corpus (see Data).

- If MADLAD is decent zero-shot, fine-tune it: it already knows the language and covers over 450 languages, which suits the portability goal.
- Otherwise fine-tune NLLB-200-distilled-600M using the ILSP recipe: add the missing polytonic characters to the tokenizer (they found 148 for NLLB), initialize each new character's embedding from its closest base letter, LoRA rank 16, alpha 32, dropout 0.05. They trained on a single L4 GPU in Colab.
- During fine-tuning, inject placeholders into training pairs (copied unchanged on both sides) so the model learns to pass them through. This is what makes masking reliable.

Not usable as translators: the Rapacz interlinear models (word-by-word glosses, New Testament only, CC BY-NC-SA). They may help as a gloss source for alignment.

## Data

The Greek sources and English references both come from Perseus, paired by their shared CTS citation scheme.

- **Source repo:** `github.com/PerseusDL/canonical-greekLit`. Files follow `data/TEXTGROUP/WORK/TEXTGROUP.WORK.VERSION.xml`; Greek editions end `perseus-grc1/2/…`, English translations `perseus-eng1/2/…`. Files ending in `1` are often not yet CTS-compliant, so prefer higher-numbered versions where they exist.
- **Pairing:** match Greek and English citation units by CTS reference (e.g. book.chapter.section). This gives unit-level alignment without any model.
- **Sentence alignment within units:** VecAlign with a Greek–English sentence embedding model (`kevinkrahn/shlm-grc-en`, or LaBSE). ILSP found VecAlign + LaBSE most accurate for long literary texts.
- **Shortcut to evaluate first:** the Hugging Face dataset `sol-r/ancient-aligned` already has 27,421 Greek–English pairs from 168 Perseus works, indexed by CTS URN. Check how it was aligned before relying on it.
- **Splits:** split train / dev / test **by work**, never by sentence, so test texts are unseen. Include some less famous works in test, since famous texts and their translations are likely in LLM training data.
- **Placeholder injection:** when building fine-tuning data, insert placeholders at random positions in both sides of some pairs.
- **Licensing:** record each file's license from its TEI header; Perseus texts are mostly CC BY-SA.

## Alignment and tag projection

Inline tags are moved to the English side through word alignment between each Greek segment and its translation.

- **Default aligner:** awesome-align (multilingual BERT based, works for any covered language pair).
- **Greek aligner:** `UGARIT/grc-alignment` (XLM-RoBERTa fine-tuned on Ancient Greek; reported AER 19.73% on grc–en). Also look at `open-greek/dragoman`, a fine-tune of it with higher reported F1 on Iliad text.
- **Projection algorithm:** for a tag covering source tokens i..j, wrap the smallest contiguous English span covering all tokens aligned to i..j. Follow Zenkel et al. (2021), who improved this basic method; their evaluation code is at `github.com/lilt/markup-tag-eval`.
- **Expansion is normal:** a single Greek participle often becomes a whole English clause. Allow one-to-many spans and never split a projected tag across non-contiguous words.
- **Nesting:** project outer tags first, then inner tags constrained to lie within the outer span.
- **Fallbacks, in order:** (1) wrap the whole sentence if nothing aligns, for tags that must keep content; (2) convert to an empty milestone at the best-guess position; (3) drop the tag and keep its attributes in a `<note type="mt-warning">` or an XML comment. Always count fallbacks per document.
- **Names:** after projection, replace the English span inside each `<persName>` / `<placeName>` with the convention-resolved form when the MT output differs.

## Validation and evaluation

Every output is checked automatically, and experiments report three groups of metrics.

| Group | Metric | How |
| --- | --- | --- |
| Structure | XML well-formedness | lxml parse succeeds |
| Structure | TEI validity | RELAX NG validation against tei\_all (or EpiDoc where applicable) |
| Structure | XML-Match, TreeSim | Tree identical to source tree / normalized tree edit distance (Zhang–Shasha), ignoring text |
| Structure | Citation preservation | % of `@n` and `@xml:id` values present and in order |
| Translation | chrF, COMET | On text with markup removed, against Perseus English for the same CTS unit |
| Translation | Node-chrF | chrF per matching text node (from the FormatRL paper) |
| Tag policy | Protected-span fidelity | % of protected spans restored byte-identical |
| Tag policy | Name accuracy | Rendered names vs a small hand-made gold list |
| Tag policy | Projection accuracy | Zenkel et al. metrics on a small hand-tagged set; fallback rate per document |

Automatic metrics do not separate good translations well for Ancient Greek, so plan a small human evaluation (for example 30–50 segments rated by a team member who reads Greek).

Systems to compare in the final experiment:

1. B0: DeepL or Google on the raw XML (naive baseline)
2. B1: segmentation only, inline tags dropped
3. B2: B1 + detag-and-project with the fine-tuned MT model
4. B3: B2 + fine-tuned placeholder/tag handling (model places tags itself), as a comparison
5. Reference: the same pipeline with an LLM as the MT engine

## Open questions and risks

**Open questions (ask the team before deciding):**

- [ ] Which hardware is available: laptop CPU only, a consumer GPU, or Colab? This decides MADLAD 3B vs NLLB-600M for fine-tuning.
- [ ] Default name convention for grc→en: Latinized or direct transliteration?
- [ ] `<del>` content and `<choice>` handling: confirm the defaults in the policy table.
- [ ] Which extra features from the proposal are in scope (for example linking original and translation passages)?

**Risks:**

- MADLAD-400's Ancient Greek quality is unknown; the bake-off may show all local models are weak zero-shot. Mitigation: fine-tuning is planned regardless.
- NMT models may mangle placeholders before fine-tuning. Mitigation: test placeholder survival in the bake-off; consider removing protected spans from the MT input and re-inserting them by alignment.
- Verse (`<l>`) projection will concentrate alignment errors. Mitigation: deferred until prose works.
- Contamination: famous texts and their translations are likely in LLM and possibly MADLAD training data, inflating scores. Mitigation: split by work and include less famous texts in test.
- Some Perseus files are not yet CTS-compliant, which breaks unit pairing. Mitigation: skip or flag them in the loader.
